# سِكّة — تنفيذ أول 10 شاشات

**الفرع:** `feat/first-10-screen-flows`  
**الهدف:** تنفيذ أول دفعة على الشاشات الفعلية في التطبيق، وليس إنشاء صور أو Preview منفصل.  
**قاعدة التحقق:** أي حالة أو مبلغ أو رحلة تظهر للمستخدم يجب أن تأتي من بيانات التطبيق الفعلية. لا نعرض نجاح دفع أو تفعيل اشتراك لمجرد إرسال طلب.

## ترتيب الشاشات المعتمد لهذه الدفعة

| # | الشاشة | موضع التنفيذ الحالي | حالة هذه الدفعة |
|---|---|---|---|
| 1 | الرئيسية | `web/src/screens/RiderWorkspace.tsx`، القسم `home` | موجودة؛ تحسين بصري |
| 2 | البحث عن رحلة | نموذج المسار والباقة داخل `RiderWorkspace.tsx`، القسم `booking` | موجودة؛ يلزم لاحقًا فصل نتائج البحث المطابقة للمسار عن إنشاء مجموعة جديدة بصورة أوضح |
| 3 | نتائج البحث | `RiderWorkspace.tsx`، القسم `trips` وعروض `rider-trip-offer` | موجودة؛ النتائج المعروضة تعتمد على عروض API المتاحة، وليست بيانات تجريبية |
| 4 | تفاصيل عرض الكابتن | نافذة `rider-trip-detail-dialog` داخل `RiderWorkspace.tsx` | موجودة؛ تعرض التفاصيل وتتيح اختيار الركوب والنزول |
| 5 | طلب الانضمام | إجراء `requestSelectedLine()` من تفاصيل العرض، مع حالة إرسال وتعطيل الزر عند نقص المواقع | موجودة؛ الإرسال لا يعني قبول الطلب أو تفعيل الاشتراك |
| 6 | متابعة اكتمال المجموعة | `GroupSummary` و`GroupDetail` في `web/src/components/workspace-shared.tsx` | تم تحسين ملخص الحالة والمقاعد ومواعيد الرحلات المسجلة |

| 8 | لوحة الكابتن | `web/src/screens/CaptainWorkspace.tsx`، القسم `offers` | موجودة؛ تعتمد على عروض ومسارات الكابتن الفعلية |
| 9 | إنشاء عرض رحلة | قسم `publish` في `CaptainWorkspace.tsx` وعمليات API الخاصة بعروض الكابتن | موجودة؛ يتطلب التحقق من بيانات الحساب والصلاحيات قبل النشر |
| 10 | إدارة المجموعة | تدفقات طلبات الكابتن/المجموعات في `CaptainWorkspace.tsx` مع مكونات المجموعة المشتركة | موجودة جزئيًا؛ يجب تدقيق اكتمال إدارة أعضاء المجموعة وحالاتها وربطها بالنموذج المعتمد قبل اعتبارها مكتملة |

## التغييرات المنفذة في هذه الدفعة

1. تحسين بصري للشاشات الحقيقية الأولى: الصفحة الرئيسية للراكب، بطاقات عروض الرحلات، نافذة تفاصيل العرض، ملخص المجموعة، ونماذج العمل على الهاتف.
2. إضافة بطاقة متابعة داخل تفاصيل المجموعة تعرض فقط بيانات متوفرة فعليًا:
   - حالة المجموعة من `group.status`.
   - المقاعد المحجوزة مقارنة بسعة الفئة.
   - عدد الرحلات المسجلة.
   - أقرب تاريخ خدمة قادم إن وجد.
   - المبلغ المستحق فقط عندما يتضمن رد API كائن اشتراك.
3. إضافة توضيح صريح بأن إنشاء المجموعة لا يعني أن الاشتراك نشط، وأن البحث عن كابتن لا يعني تأكيد الرحلة.
4. لم تتم إضافة بيانات وهمية أو تغيير قواعد الدفع أو تأكيد الطلبات من الواجهة دون استجابة API.

## ما لا أعتبره منجزًا بعد

- فصل كل شاشة من العشرة إلى Route مستقل إذا كانت حاليًا حالة داخل Workspace أو نافذة تفاصيل.
- اختبار end-to-end لكل المسارات من الرئيسية حتى طلب الانضمام ثم متابعة المجموعة.
- تدقيق نهائي لتطابق نموذج عروض الكابتن والمجموعات وطلبات الراكب مع قرارات المنتج الحالية.
- بناء صفحة اشتراك نشط مستقلة إذا كانت البيانات الخلفية لا توفر بعد كيانًا وحالة اشتراك مكتملين لكل رحلة.
- تأكيد البناء والاختبارات على GitHub Actions لهذه الدفعة الجديدة.

**الخلاصة:** هذه الدفعة تحسّن واجهات فعلية وتضيف متابعة حالة مبنية على بيانات حقيقية. لكنها لا تعني أن أول عشر شاشات اكتملت وظيفيًا بالكامل؛ الحالات الموضحة أعلاه هي حدود التنفيذ الحالية.
