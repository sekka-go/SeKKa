# 1. الهدف من الخطة

تحدد هذه الوثيقة طريقة تنفيذ مشروع SeKKa على مراحل واضحة وقابلة للقياس والتحقق.

الهدف ليس كتابة أكبر قدر من الكود بأسرع وقت، وإنما الوصول إلى تطبيق متكامل يحقق متطلبات العمل المعتمدة، ويعمل بصورة صحيحة وآمنة، ويمكن اختباره وصيانته وتطويره.

يجب أن تربط الخطة بين:

1. متطلبات المنتج.
2. القرارات المعتمدة.
3. القرارات المفتوحة.
4. خرائط الشاشات.
5. التصميم وتجربة المستخدم.
6. الواجهة الأمامية.
7. الخدمات الخلفية.
8. قاعدة البيانات.
9. المصادقة والصلاحيات.
10. الاشتراكات والمطابقة.
11. الدفع والتأكيدات.
12. الإشعارات.

يجب أن تكون لكل مرحلة أهداف واضحة، ومخرجات فعلية، ومعايير قبول يمكن التحقق منها.

# 2. القاعدة الأساسية للتنفيذ

## 2.1 لا تبدأ من الصفر دون فحص

يجب فحص المشروع الحالي قبل تحديد المهام التنفيذية النهائية.

قد تكون بعض الوظائف منفذة بالكامل، أو منفذة جزئيًا، أو موجودة في الواجهة فقط، أو موجودة في قاعدة البيانات دون تكامل فعلي.

لذلك لا يجوز:

- إعادة بناء وظيفة موجودة دون داعٍ.
- إنشاء جداول مكررة.
- إعادة كتابة ملفات تعمل بالفعل لمجرد تغيير أسلوب البرمجة.
- حذف وظائف قائمة قبل فهم اعتمادياتها.
- إعلان اكتمال المشروع بناءً على تقارير قديمة.
- افتراض أن وجود ملف يعني أن وظيفته تعمل.

يجب أن تعتمد الخطة النهائية على فحص الكود وقاعدة البيانات والاختبارات الفعلية.

## 2.2 لا تخلط بين التخطيط والتنفيذ

هناك فرق بين:

- المهمة المخططة.
- المهمة التي بدأ تنفيذها.
- المهمة التي انتهى تعديل كودها.
- المهمة التي اجتازت الاختبارات.
- المهمة التي تم التحقق من عملها في البيئة المستهدفة.

يجب توثيق الحالة الحقيقية لكل مهمة.

## 2.3 لا تغيّر قواعد العمل

يجب أن يتوافق التنفيذ مع أحدث نسخة معتمدة من:

- Master PRD.
- `DECISION_LOG.md`.
- `DESIGN.md`.
- `ARCHITECTURE.md`.
- خرائط الشاشات وتدفقات الاستخدام.

إذا تعارضت الوثائق، فيجب تسجيل التعارض قبل التنفيذ.

لا يجوز اتخاذ قرار تجاري جديد لمجرد تسهيل البرمجة.

# 3. مصادر الحقيقة

ترتيب الرجوع إلى الوثائق:

1. أحدث Master PRD معتمد.
2. `DECISION_LOG.md`.
3. خرائط الشاشات المعتمدة.
4. `DESIGN.md`.
5. `ARCHITECTURE.md`.
6. `IMPLEMENTATION_PLAN.md`.
7. الكود الفعلي.
8. الاختبارات والتقارير السابقة.

يجب استخدام الكود الفعلي لتحديد ما هو موجود وما يعمل، بينما تحدد الوثائق المعتمدة ما ينبغي أن يفعله النظام.

لا يجوز استخدام التنفيذ الحالي لتبرير مخالفة متطلب معتمد.

إذا ظهر تعارض:

1. وثّق المتطلب المتعارض.
2. حدد الملفات أو الجداول المتأثرة.
3. اشرح أثر التعارض.
4. حدد ما إذا كان يتطلب قرارًا من صاحب المشروع.
5. لا تنفذ تغييرًا جوهريًا قبل حسمه.

# 4. حالات المهام

يجب استخدام الحالات التالية في متابعة التنفيذ.

| Status | المعنى |
|---|---|
| NOT_STARTED | لم يبدأ العمل |
| AUDITING | جارٍ فحص التنفيذ الحالي |
| BLOCKED | متوقف بسبب اعتماد أو مشكلة |
| READY | المتطلبات واضحة ويمكن البدء |
| IN_PROGRESS | جارٍ التنفيذ |
| IMPLEMENTED | تم تنفيذ الكود، لكن التحقق قد لا يكون مكتملًا |
| TESTING | جارٍ التحقق والاختبار |
| VERIFIED | اجتازت المهمة معايير التحقق المحددة |
| FAILED | فشل التنفيذ أو الاختبارات |
| DEFERRED | مؤجلة بقرار موثق |
| NOT_REQUIRED | ثبت أنها خارج نطاق المرحلة |

لا تستخدم `VERIFIED` دون دليل على تنفيذ الفحوص المطلوبة.

ولا تستخدم `NOT_REQUIRED` لمجرد أن الوظيفة صعبة أو غير منفذة.

# 5. تصنيف الأولويات

| Priority | المعنى |
|---|---|
| P0 | مانع أمني أو وظيفي أو تجاري يمنع الاعتماد على النظام |
| P1 | متطلب أساسي للمرحلة المستهدفة |
| P2 | تحسين مهم بعد استقرار الوظائف الأساسية |
| P3 | تحسين اختياري أو تطوير مستقبلي |

يجب تحديد الأولوية الفعلية لكل مهمة بعد مقارنة الـ PRD بالنظام الحالي.

لا تُستخدم الأولويات لتجاوز قرار تجاري مفتوح.

- [ ] مراجعة إعدادات المصادقة.

- [ ] مراجعة الأسرار.
- [ ] مراجعة سجلات الأخطاء.

### TASK-1202 — مراجعة البيانات

- [ ] مراجعة Migrations المطلوبة.
- [ ] التأكد من توافق الكود مع المخطط.
- [ ] التأكد من عدم وجود تغييرات مدمرة غير معتمدة.
- [ ] توثيق النسخ الاحتياطي أو خطة الاستعادة إذا كانت متاحة.
- [ ] التحقق من عدم استخدام بيانات اختبار في الإنتاج.

### TASK-1203 — التحقق من النشر

- [ ] تشغيل Build.
- [ ] تشغيل الاختبارات المطلوبة.
- [ ] تنفيذ النشر بالطريقة المعتمدة.
- [ ] التحقق من نجاح النشر.
- [ ] اختبار المسارات الأساسية بعد النشر.
- [ ] التحقق من اتصال الخدمات.
- [ ] التحقق من سجلات الأخطاء.
- [ ] توثيق النتيجة.

### TASK-1204 — قرار الإطلاق

يجب إعداد تقرير يتضمن:

- ما الذي تم التحقق منه.
- ما الذي لم يتم التحقق منه.
- المخاطر المتبقية.
- العيوب المعروفة.
- القرارات المفتوحة.
- الوظائف المؤجلة.
- نتيجة اختبارات الأمان.
- نتيجة اختبارات التدفقات الأساسية.
- التوصية النهائية بشأن الإطلاق.

لا يجوز إعلان الجاهزية للإنتاج إذا كانت هناك مخاطر حرجة غير معالجة أو غير مقبولة.

# 21. تتبع المتطلبات

يجب ربط كل متطلب في الـ PRD بمهمة تنفيذ واضحة.

أنشئ أو حدّث `REQUIREMENTS_TRACEABILITY.md`.

يجب أن يحتوي على الأقل على:

| Requirement ID | المتطلب | المصدر | الشاشة | الخدمة | قاعدة البيانات | الاختبار | الحالة |
|---|---|---|---|---|---|---|---|
| REQ-001 | يُنقل من الـ PRD | اسم المستند والقسم | المسار الفعلي | الملف أو الدالة | الجدول أو القيد | الاختبار | الحالة الفعلية |

قواعد مهمة:

- استخدم معرفات المتطلبات الأصلية إن وجدت.
- لا تختلق معرفات رسمية.
- لا تترك متطلبًا أساسيًا دون حالة.
- لا تعتبر وجود شاشة كافيًا.
- لا تعتبر وجود جدول كافيًا.
- لا تعتبر وجود اختبار دون تشغيله دليلًا على نجاحه.
- وثّق المتطلبات التي لا يمكن ربطها بالتنفيذ الحالي.

## معايير عامة

- [ ] المتطلب واضح ومرتبط بمصدر معتمد.
- [ ] لا يوجد تعارض غير محسوم مع القرارات.
- [ ] تم فحص التنفيذ الحالي.
- [ ] تم تنفيذ التغيير المطلوب.
- [ ] تم تحديث الأنواع والواجهات المرتبطة.
- [ ] تم تحديث قاعدة البيانات عند الحاجة.
- [ ] تم تطبيق الصلاحيات المناسبة.
- [ ] تمت معالجة حالات الفشل.
- [ ] تم تحديث الاختبارات.
- [ ] تم تشغيل الاختبارات المطلوبة.
- [ ] تم توثيق النتيجة.

- [ ] البيانات تظل متسقة عند الفشل.
- [ ] تم اختبار الحالات السلبية.

# 23. قواعد تحديث الخطة

يجب تحديث `IMPLEMENTATION_PLAN.md` عند:

- اكتشاف أن وظيفة منفذة بالفعل.
- اكتشاف أن وظيفة غير موجودة.
- اكتشاف مشكلة تمنع التنفيذ.
- اعتماد قرار جديد.
- تغيير نطاق المرحلة.
- إتمام مهمة.
- فشل اختبار.
- اكتشاف خطر أمني.
- تأجيل وظيفة بقرار موثق.
- تغيير الاعتماديات بين المهام.

يجب أن تعكس الخطة الواقع الحالي، لا أن تظل قائمة مهام ثابتة منفصلة عن المشروع.

لا تُحذف المهام المكتملة؛ تُحدّث حالتها وتُحفظ الأدلة المهمة.

# 24. قواعد العمل مع Codex

يجب على Codex اتباع القواعد التالية:

1. اقرأ أحدث الوثائق المعتمدة قبل التنفيذ.
2. افحص المستودع قبل تعديل الملفات.
3. لا تفترض أن المشروع يبدأ من الصفر.
4. لا تنفذ كل المراحل دفعة واحدة دون مراجعة.
5. لا تغير قواعد العمل.
6. لا تحسم القرارات المفتوحة.
7. لا تضف جداول مكررة.
8. لا تعدل قاعدة البيانات الإنتاجية دون التأكد من البيئة والصلاحيات وأثر العملية.
9. لا تضع أسرارًا في الكود.
10. لا تتجاوز RLS لإصلاح مشكلة.
11. لا تعتبر الواجهة وحدها تنفيذًا للوظيفة.
12. لا تستبدل التنفيذ الحقيقي ببيانات وهمية.
13. لا تعلن نجاح اختبارات لم تُشغّل.
14. لا تعلن نجاح النشر دون تحقق.
15. لا تنفذ تغييرات مدمرة دون مراجعة وموافقة مناسبة.
16. لا تضف مكتبات أو خدمات دون تقييم.
17. حدّث التوثيق عند تغيير المعمارية أو قواعد التنفيذ.
18. اربط كل مهمة بمتطلب واضح.
19. وثّق ما لم تستطع التحقق منه.
20. قدّم تقريرًا دقيقًا بعد كل مرحلة.

## 24.1 أسلوب التنفيذ

الأفضل أن يتم العمل على دفعات صغيرة ومترابطة:

1. تحديد نطاق الدفعة.
2. فحص الاعتماديات.
3. تنفيذ التغييرات.
4. تشغيل الفحوص المناسبة.
5. مراجعة النتائج.
6. تحديث الوثائق.
7. تحديد الدفعة التالية.

لا تبدأ مرحلة تعتمد على قرار مفتوح قبل حسمه.

يمكن تنفيذ الأعمال المستقلة التي لا تتأثر بالقرار بالتوازي إذا كان ذلك آمنًا.

# 25. التقرير المطلوب بعد كل دفعة

يجب أن يتضمن التقرير:

## A. Summary

ملخص واضح لما تم تنفيذه.

## B. Changed Files

قائمة الملفات التي تم تعديلها أو إنشاؤها.

## C. Requirements

المتطلبات التي تغطيها التغييرات.

## D. Database

الجداول أو السياسات أو الدوال أو Migrations التي تغيرت.

إذا لم تحدث تغييرات في قاعدة البيانات، اذكر ذلك.

## E. Security

الصلاحيات والتحققات التي تم تنفيذها أو اختبارها.

## F. Tests

| Test | Command | Result | Notes |
|---|---|---|---|
| Typecheck | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Lint | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Unit Tests | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Integration Tests | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Build | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |

لا تضع `PASS` إلا إذا نُفذ الاختبار ونجح فعلًا.

## G. Remaining Issues

المشكلات التي لم تُحل.

## H. Decisions Needed

القرارات التي تحتاج إلى موافقة.

## I. Next Step

الخطوة التالية المقترحة وسبب ترتيبها.

# 26. شروط إنهاء المشروع

لا يُعتبر الإصدار جاهزًا لمجرد اكتمال جميع المهام المكتوبة في هذه الخطة.

يجب التحقق من:

- اكتمال المتطلبات الأساسية المعتمدة.
- تطابق الوظائف مع الـ PRD.
- توافق التنفيذ مع القرارات المعتمدة.
- اكتمال تدفقات المستخدم الأساسية.
- سلامة عمليات الاشتراك والمطابقة والدفع ضمن نطاق الإصدار.
- حماية البيانات والصلاحيات.
- سلامة قاعدة البيانات.
- نجاح الاختبارات المطلوبة.
- عدم وجود عيوب حرجة غير مقبولة.
- اكتمال إعدادات النشر المطلوبة.
- توثيق القيود والقرارات المفتوحة.
- وجود تقرير واضح عن الجاهزية.

أي وظيفة مؤجلة يجب أن تكون مؤجلة بوضوح، لا أن تظهر للمستخدم وكأنها تعمل.

# 27. تعليمات البداية

عند استلام هذه الخطة لأول مرة، لا تبدأ بتنفيذ جميع المراحل.

ابدأ بالمرحلة صفر فقط.

المطلوب:

1. فحص المشروع الحالي.
2. قراءة الوثائق المعتمدة.
3. ربط المتطلبات بالتنفيذ الفعلي.
4. تحديد الفجوات والمخاطر.
5. تشغيل الفحوص التي يمكن تشغيلها بأمان.
6. تحديث خطة التنفيذ وفق النتائج.
7. عرض التقرير للمراجعة.

لا تعدل الكود في مرحلة التدقيق الأولي.

بعد مراجعة نتائج التدقيق واعتماد خطة التنفيذ، يبدأ التنفيذ على دفعات محددة.

**القاعدة النهائية:**

الخطة ليست دليلًا على أن المشروع مكتمل؛ إنها وسيلة لتحديد ما يجب تنفيذه، وما تم تنفيذه فعلًا، وما تم التحقق منه بالأدلة.
