# 1. الهدف من الوثيقة

تحدد هذه الوثيقة خطة تنفيذ مشروع SeKKa بصورة منظمة وقابلة للقياس والتحقق.

الهدف ليس مجرد كتابة الكود، وإنما الوصول إلى تطبيق متكامل يحقق متطلبات العمل المعتمدة، ويعمل بصورة صحيحة وآمنة، ويمكن اختباره وصيانته وتطويره.

يجب أن تربط الخطة بين:

1. متطلبات المنتج.
2. القرارات التجارية المعتمدة.
3. القرارات المفتوحة والمؤجلة.
4. خرائط الشاشات وتدفقات الاستخدام.
5. التصميم ونظام المكونات.
6. الواجهة الأمامية.
7. الخدمات الخلفية.
8. قاعدة البيانات.
9. المصادقة والصلاحيات.
10. الاشتراكات والمطابقة.
11. الدفع وتأكيد الاستلام.
12. الإشعارات.
13. لوحة الإدارة.
14. الاختبارات.
15. النشر والتشغيل.

يجب أن تكون كل مهمة محددة النطاق، ولها مخرجات واضحة، ومعايير قبول قابلة للتحقق.

هذه الوثيقة خطة عمل وليست إثباتًا على أن أي وظيفة قد نُفذت بالفعل.

# 2. المبادئ الأساسية

## 2.1 افحص الموجود أولًا

لا تفترض أن المشروع يبدأ من الصفر.

قبل تنفيذ أي مرحلة، افحص:

- الكود الحالي.
- ملفات المشروع.
- قاعدة البيانات.
- ملفات Migration.
- وظائف الخادم.
- سياسات الصلاحيات.
- الشاشات الموجودة.
- الاختبارات.
- إعدادات البناء والنشر.
- الوثائق المعتمدة.

حدد لكل وظيفة حالتها الحقيقية:

- منفذة ومتحقق منها.
- منفذة جزئيًا.
- موجودة في الواجهة فقط.
- موجودة في الخلفية فقط.
- موجودة دون تكامل صحيح.
- غير منفذة.
- معطلة.
- يتعذر التحقق منها.

لا تُعد بناء وظيفة موجودة وتعمل بصورة صحيحة دون سبب واضح.

## 2.2 لا تخلط بين وجود الكود واكتمال الوظيفة

وجود شاشة لا يعني أن الوظيفة مكتملة.

وجود جدول لا يعني أن تدفق العمل يعمل.

وجود دالة لا يعني أنها آمنة.

وجود اختبار لا يعني أنه نجح.

وجود تقرير سابق لا يعني أن الحالة الحالية مطابقة له.

لا تُعتبر المهمة مكتملة إلا بعد تنفيذ معايير القبول وتشغيل الفحوص المناسبة.

## 2.3 لا تخترع قواعد عمل

يجب أن يتوافق التنفيذ مع أحدث نسخة معتمدة من:

- Master PRD.
- `DECISION_LOG.md`.
- `DESIGN.md`.
- `ARCHITECTURE.md`.
- خرائط الشاشات وتدفقات الاستخدام.

عند وجود قرار مفتوح يؤثر على التنفيذ:

1. حدد القرار.
2. حدد المهام المتأثرة.
3. أوقف الجزء الذي يتطلب هذا القرار.
4. نفذ الأعمال المستقلة عنه فقط إذا كان ذلك آمنًا.
5. اطلب اعتماد القرار عند الحاجة.

لا تستبدل القرار التجاري بتخمين تقني.

## 2.4 حافظ على النطاق

لا تضف وظائف جديدة إلى الإصدار الأول لمجرد سهولة تنفيذها.

لا تنفذ وظائف مؤجلة دون اعتماد.

لا تحذف وظائف معتمدة دون توثيق وموافقة.

لا توسع نطاق المشروع أثناء إصلاح مشكلة إلا إذا كان التغيير ضروريًا ومبررًا.

# 3. مصادر الحقيقة

قبل أي تنفيذ، اقرأ أحدث الوثائق المعتمدة المتاحة.

الترتيب المرجعي:

1. أحدث Master PRD معتمد: لقواعد العمل والنطاق.
2. `DECISION_LOG.md`: لحالة القرارات المعتمدة والمفتوحة.
3. خرائط الشاشات المعتمدة: لتدفقات الاستخدام والشاشات.
4. `DESIGN.md`: لقواعد التصميم وتجربة المستخدم.
5. `ARCHITECTURE.md`: للبنية التقنية وحدود المكونات.
6. `IMPLEMENTATION_PLAN.md`: لترتيب التنفيذ ومعايير القبول.
7. الكود الفعلي: لتحديد الحالة الحالية للتنفيذ.
8. الاختبارات وسجلات التشغيل: للتحقق من السلوك الفعلي.

إذا تعارضت الوثائق:

- لا تختر نسخة عشوائيًا.
- لا تفترض أن الأحدث زمنيًا هو المعتمد تلقائيًا دون التحقق.
- وثق التعارض.
- حدد أثره على التنفيذ.
- اطلب الحسم إذا كان التعارض متعلقًا بقرار عمل.

الكود الحالي يوضح ما نُفذ، لكنه لا يُعد موافقة على مخالفة المتطلبات المعتمدة.

# 4. حالات المهام

يجب استخدام الحالات التالية في متابعة التنفيذ.

| الحالة | المعنى |
|---|---|
| NOT_STARTED | لم يبدأ العمل |
| AUDITING | جارٍ فحص التنفيذ الحالي |
| BLOCKED | متوقف بسبب قرار أو اعتماد أو مشكلة |
| READY | المتطلبات واضحة ويمكن البدء |
| IN_PROGRESS | جارٍ التنفيذ |
| IMPLEMENTED | تم تعديل الكود، لكن التحقق غير مكتمل بالضرورة |
| TESTING | جارٍ تشغيل الاختبارات |
| VERIFIED | اجتازت المهمة معايير القبول المحددة |
| FAILED | فشل التنفيذ أو أحد الاختبارات المطلوبة |
| DEFERRED | مؤجلة بقرار موثق |
| NOT_REQUIRED | ثبت أنها خارج نطاق الإصدار المستهدف |

لا تستخدم `VERIFIED` دون دليل.

لا تستخدم `NOT_REQUIRED` لمجرد أن الوظيفة صعبة أو غير منفذة.

يجب أن تتضمن المهام المكتملة مرجعًا إلى نتائج الفحص أو الاختبار ذات الصلة.

# 24. قواعد التنفيذ باستخدام Codex

يجب على Codex الالتزام بما يلي:

1. اقرأ أحدث الوثائق المعتمدة قبل التنفيذ.
2. افحص المستودع قبل تعديل الملفات.
3. لا تفترض أن المشروع يبدأ من الصفر.
4. لا تنفذ جميع المراحل دفعة واحدة دون مراجعة.
5. لا تغير قواعد العمل.
6. لا تحسم القرارات المفتوحة.
7. لا تنشئ جداول مكررة.
8. لا تعدل قاعدة الإنتاج دون التأكد من البيئة والأثر والصلاحيات.
9. لا تضع أسرارًا في الكود.
10. لا تتجاوز RLS لإصلاح مشكلة.
11. لا تعتبر الواجهة وحدها تنفيذًا للوظيفة.
12. لا تستبدل التنفيذ الحقيقي ببيانات وهمية.
13. لا تعلن نجاح اختبار لم يُشغّل.
14. لا تعلن نجاح النشر دون تحقق.
15. لا تنفذ تغييرات مدمرة دون مراجعة مناسبة.
16. لا تضف مكتبات دون تقييم الحاجة والأثر.
17. حدّث التوثيق عند تغيير المعمارية.
18. اربط كل مهمة بمتطلب واضح.
19. وثّق ما تعذر التحقق منه.
20. قدم تقريرًا دقيقًا بعد كل دفعة.

## أسلوب التنفيذ

لكل دفعة:

1. حدد نطاقها.
2. افحص الاعتماديات.
3. نفذ التغييرات المطلوبة فقط.
4. شغّل الفحوص المناسبة.
5. راجع النتائج.
6. حدّث الوثائق.
7. حدد الخطوة التالية.

يمكن تنفيذ المهام المستقلة بالتوازي إذا لم يؤدِ ذلك إلى تعارض في الملفات أو القرارات أو قاعدة البيانات.

# 25. التقرير المطلوب بعد كل دفعة

يجب أن يتضمن التقرير:

## A. Summary

ملخص ما تم تنفيذه فعليًا.

## B. Changed Files

قائمة الملفات التي تم إنشاؤها أو تعديلها.

## C. Requirements

المتطلبات التي تغطيها التغييرات.

## D. Database

الجداول والسياسات والدوال وملفات Migration التي تغيرت.

إذا لم تحدث تغييرات في قاعدة البيانات، اذكر ذلك صراحةً.

## E. Security

الصلاحيات والتحققات التي تم تنفيذها أو اختبارها.

## F. Tests

| Test | Command | Result | Notes |
|---|---|---|---|
| Typecheck | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Lint | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Unit Tests | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Integration Tests | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |
| Build | الأمر الفعلي | PASS/FAIL/NOT_RUN | التفاصيل |

لا تستخدم `PASS` إلا إذا تم تشغيل الاختبار ونجح بالفعل.

## G. Remaining Issues

المشكلات التي لم تُحل.

## H. Decisions Needed

القرارات التي تحتاج إلى اعتماد.

## I. Next Step

الخطوة التالية المقترحة وسبب ترتيبها.

# 26. شروط جاهزية الإصدار

لا يُعتبر الإصدار جاهزًا لمجرد اكتمال قائمة المهام.

يجب التحقق من:

- اكتمال المتطلبات الأساسية المعتمدة.
- تطابق الوظائف مع الـ PRD.
- توافق التنفيذ مع القرارات المعتمدة.
- اكتمال تدفقات المستخدم الأساسية.
- سلامة الاشتراكات والمطابقة والدفع ضمن نطاق الإصدار.
- حماية البيانات والصلاحيات.
- سلامة قاعدة البيانات.
- نجاح الاختبارات المطلوبة.
- عدم وجود عيوب حرجة غير مقبولة.
- اكتمال إعدادات النشر المطلوبة.
- توثيق القيود والقرارات المفتوحة.
- وجود تقرير موثق عن الجاهزية.

أي وظيفة مؤجلة يجب أن تكون موثقة بوضوح، وألا تظهر للمستخدم وكأنها تعمل.

# 27. نقطة البداية الإلزامية

عند استلام هذه الخطة لأول مرة:

**ابدأ بالمرحلة صفر فقط.**

المطلوب:

1. فحص المشروع الحالي.
2. قراءة أحدث الوثائق المعتمدة.
3. حصر الوظائف الموجودة.
4. ربط المتطلبات بالتنفيذ الفعلي.
5. تحديد الفجوات والمخاطر.
6. تشغيل الفحوص الممكنة بأمان.
7. تحديث خطة التنفيذ بناءً على النتائج.
8. تقديم تقرير للمراجعة.

لا تعدل الكود الوظيفي خلال التدقيق الأولي.

بعد مراجعة نتائج التدقيق واعتماد خطة التنفيذ، ابدأ التنفيذ على دفعات واضحة ومحددة.

# 28. القاعدة النهائية

الخطة ليست دليلًا على اكتمال المشروع.

إنها وسيلة لتحديد:

- ما الذي يجب تنفيذه.
- ما الذي نُفذ بالفعل.
- ما الذي تم التحقق منه.
- ما الذي لا يزال ناقصًا.
- ما الذي يحتاج إلى قرار.
- ما الذي يمنع الإطلاق.

**لا تعلن اكتمال أي وظيفة أو مرحلة دون دليل فعلي يتناسب مع طبيعتها.**
