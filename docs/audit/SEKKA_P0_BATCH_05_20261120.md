# seKKa P0 batch 05 — Capacity transitions, accurate Captain counts, safe concurrency gate
Date: 20 November 2026 · Work on PR #185 only · DB target: Staging `zgcvumykzivsvnlflbyp`.

## Changes made
- Added `v31_notify_route_capacity_transition()` with one booking trigger: when an insert reaches exactly the approved seat capacity, the Captain receives `route_capacity_full`; when cancellation crosses from full to not-full, the Captain receives `route_seat_reopened`. Notices are in the same transaction as the booking or cancellation. No departure date, payment, cancellation penalty, or operational-trip model was invented.
- Added `v31_captain_route_capacity_summary(p_route)` with ownership filter `auth.uid() = captain_id`, actual aggregate of active seats and exact remaining count. This replaces the Captain screen's capped 500-booking client read (which could otherwise silently undercount).
- Captain `My trips` shows remaining seats and full-capacity status. It preserves the approved typography and colors.
- Mocked browser regression covers remaining seats and full transition on an existing published route.
- Added an **opt-in** staging-only real concurrency test `web/scripts/staging-parallel-last-seat.mjs`, available as `npm run test:staging:parallel-seats`. It requires an approved Captain plus TWO DIFFERENT valid Google Rider sessions and a published route **explicitly named `STAGING CONCURRENCY QA...`** with one seat left. It is forbidden against Production and non-QA routes. Winner is cancelled; a cancelled QA booking and audit notifications remain in Staging.

## Verified on Staging
- Rollback-only booking test: one reserved seat caused exactly one full-capacity notice; its cancellation caused exactly one reopened-seat notice; no test booking/notice persisted.
- Permission probe: only the logged-in Captain receives capacity details; unrelated authenticated users get zero rows; anonymous callers have no permission to execute.
- Separate SQL tool calls attempted route-lock contention, but the tool runner did not guarantee simultaneous independent sessions and reported `CONCURRENCY_TEST_NO_LOCK_CONTENTION`. **This is NOT a successful parallel-booking test**. There was no durable test booking from that attempted probe.
