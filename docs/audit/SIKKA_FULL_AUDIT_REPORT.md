# تقرير تدقيق سِكّة الشامل

**التاريخ:** 10 أكتوبر 2026
**النطاق:** مراجعة ساكنة للكود والمخطط والترجمات، فحوصات محلية، وتجربة واجهات عامة محلية.
**الحالة:** اكتملت مراجعة Phase 2 المحلية والفحوص المتاحة؛ الإصدار غير جاهز للتحقق الإنتاجي بسبب مخاطر معاملات قاعدة البيانات وتعذر تشغيل Supabase المحلي.

## الخلاصة

- نجحت فحوصات الواجهة والخادم المحلية: lint وTypeScript وPWA وbuild، و209 اختبارًا من 209.
- أصلحت أخطاء إنجليزية كانت تغيّر معنى اسم التطبيق والمركبات والمسارات والوحدات.
- وجدت خطر سباق على سعة المجموعة في مسار الانضمام، وسبعة أزواج من ملفات migrations المتطابقة بأسماء إصدار مختلفة.
- لم تتصل المراجعة بمشروع Supabase بعيد أو ببيانات إنتاج. تعذر تشغيل قاعدة Supabase محليًا لعدم عمل Docker؛ لذلك بقيت اختبارات pgTAP وقيود SQL غير متحققة وقت التشغيل.

## Phase 2 — تدقيق مستقل واختبارات عدائية

**التاريخ:** 10 أكتوبر 2026. أُعيد فحص الفرع `fix/audit-log-migration-version` والـ commit `2166d1b` والتغييرات الموجودة قبل البدء. حُفظت ملفات المستخدم غير المتتبعة كما هي. لم أستخدم أي مشروع Supabase بعيد أو بيانات حقيقية، ولم أنشر أو أدمج تغييرات.

### ملخص التحقق والإصلاحات

- فحصت مراجع 106 فروع توجيه في `supabase/functions/sekka-api/index.ts`، ومخططات 51 جدولًا في migrations، وسياسات التخزين، واختبارات pgTAP الموجودة. هذا فحص مصدري؛ لا يعني تنفيذ كل مسار أو إثبات الصلاحيات الفعلية.
- أصلحت تسريبًا مؤكدًا في عرض اشتراك المجموعة: كان الاختيار يقرأ اشتراكًا من المجموعة من دون ربطه بعضوية الراكب الذي يطلب العرض. أصبح الخادم يحدد عضوية الراكب النشط أولًا، ثم يستعلم عن اشتراك ذلك العضو فقط. أضيف اختباران على اختيار العضوية؛ اجتازا، لكن اختبار endpoint على PostgreSQL لم يتوفر.
- أصلحت حدّ حجم JSON: كان `req.text()` يحمّل الجسم كاملًا قبل فحص حد 1 ميجابايت. أصبحت القراءة متدفقة ومحدودة بالبايت، وتتوقف وتلغي القراءة عند تجاوز الحد وتعيد API حالة 413. اجتازت اختبارات UTF-8 والحد الدقيق والجسم الزائد وإلغاء القراءة وJSON غير الصالح.
- نظفت ملاحظات lint في Edge handler (عمليات `async` بلا انتظار، متغير قابل لإعادة الإسناد، ومعامل غير مستخدم). استُثني استيراد `npm:` وحده من قاعدة lint العامة لأنه تنسيق الاعتماد المستخدم لدالة Supabase.
- أصلحت الترجمات الإنجليزية في `web/src/i18n/locales/en.json` في المرحلة السابقة؛ بقيت التغييرات المحلية موجودة ولم تُنشر.

## سجل العيوب حسب الأولوية

### P1 — انضمام الركاب قد يتجاوز سعة المجموعة عند التزامن

في مسار `POST /rider/pool/groups/:id/join` يقرأ Edge Function أعضاء المجموعة ويفحص المقاعد، ثم ينتظر حساب المسار والسعر، وبعدها يُدخل العضو ويحدّث المجموعة. لا توجد معاملة ذرية أو قفل للمجموعة حول الفحص والإدخال. قيد قاعدة البيانات يمنع تكرار الراكب نفسه في المجموعة، لكنه لا يمنع مجموع مقاعد الأعضاء من تجاوز السعة.

إذا وصل طلبا راكبين مختلفين للمقعد الأخير بالتزامن، يمكن أن ينجح فحص السعة لكليهما. هذا استنتاج من ترتيب العمليات والقيود الحالية؛ لم يُجر اختبار تزامن على PostgreSQL.

**المعالجة المقترحة:** نقل الفحص والإضافة وتحديث السعر إلى RPC معاملاتي يقفل صف المجموعة، يعيد حساب المقاعد داخل القفل، ويرفض الطلب الزائد. أضف اختبارًا متزامنًا يثبت أن طلبًا واحدًا فقط يحجز المقعد الأخير.

الأدلة: [مسار الانضمام في Edge Function](../../supabase/functions/sekka-api/index.ts#L1308)، [قيود pool_members الحالية](../../supabase/migrations/20261001000000_postgres_baseline.sql#L159).

النسخة الأساسية تحتوي `CREATE TABLE` غير قابل لإعادة التطبيق، مثل إنشاء `public.users`؛ لذلك من المرجح أن تمر إعادة ضبط نظيفة على النسخة الثانية من المخطط وتفشل. لم أعدّل هذه الملفات لأن حالة migration history على المشروع البعيد غير معروفة، ولأن إعادة الضبط المحلية لم تصل إلى قاعدة بيانات.

**المعالجة المقترحة:** قارن `supabase migration list` بين سجل الإنتاج والملفات أولًا، ثم حضّر إصلاحًا يحافظ على سجل الإصدارات المنشورة. لا تحذف أو تعِد تسمية migration مطبقة على الإنتاج.

### P2 — تثبيت نوع الحساب غير محمي بقاعدة البيانات كقيد مستقل

جدول `users` يسمح بقيم `rider` و`captain` و`admin`، ولم أجد trigger يمنع تغيير `users.role`. التسجيل عبر Edge Function يحصر القيم في `rider` و`captain`، وتعديل ملف المستخدم الإداري لا يقبل حقل الدور؛ كما أن صلاحيات جداول `public` محجوبة عن `anon` و`authenticated`. هذه الضوابط تخفف الخطر الحالي، لكنها لا تحقق قفل الدور كقاعدة بيانات مستقلّة إذا أُضيف مسار خدمة جديد أو أسيء استخدام مفتاح الخدمة.

**المعالجة المقترحة:** أضف trigger يمنع تغيير الدور بعد الإنشاء، وحدد إجراءً إداريًا صريحًا فقط إن كانت ترقية الحسابات مطلبًا. أضف اختبار pgTAP يثبت رفض تغيير الدور من جميع المسارات غير المصرح بها.

الأدلة: [تعريف users](../../supabase/migrations/20261001000000_postgres_baseline.sql#L6)، [تقييد التسجيل](../../supabase/functions/sekka-api/index.ts#L985)، [منع صلاحيات SQL المباشرة](../../supabase/migrations/20261001000000_postgres_baseline.sql#L476).

### P2 — اختبارات PostgreSQL لا تعمل محليًا ولا تظهر في CI الحالي

تشمل المستودعات اختبارات SQLite للخادم وملفي pgTAP لـ Supabase، لكن workflow الحالي لا يشغّل `supabase db reset` أو `supabase test db`. محاولة `supabase test db --local` فشلت لأن `127.0.0.1:54322` لا يستجيب؛ كما تعذر اتصال Supabase CLI بمحرك Docker المحلي. لا يوجد مشروع Supabase مرتبط في هذا الـ checkout.

**المعالجة المقترحة:** أضف job قاعدة بيانات في CI يشغّل migration reset ثم pgTAP على قاعدة مؤقتة، وأضف له اختبارات RLS وقفل الدور وتزامن آخر مقعد. لا توجه هذه الاختبارات إلى قاعدة الإنتاج.

الأدلة: [workflow الخاص بالتوجيه](../../.github/workflows/sekka-routing.yml)، [اختبارات قاعدة Supabase](../../supabase/tests).

### P2 — متطلبات التسجيل في وثائق المرحلة تختلف عن التطبيق

وثائق مهام المرحلة تطلب تأكيد البريد وTurnstile، بينما التطبيق الحالي يستخدم رقم الهاتف وكلمة المرور وتحقق الهاتف عبر Telegram، مع حدود محاولات حسب عنوان IP ورقم الهاتف. لم أجد تكامل Turnstile في واجهة التطبيق أو Edge Function. هذا اختلاف متطلبات يحتاج قرار منتج؛ لم أغيّر تدفق التسجيل أو التحقق.

نجح البناء، لكنه أصدر تحذيرًا لأن الحزمة الرئيسية بلغت **624.75 kB** بعد التصغير (**166.27 kB gzip**) مقابل عتبة التحذير 500 kB. هذا ليس فشلًا وظيفيًا، لكنه يستحق تقسيمًا حسب المسارات بعد قياس أثره على زمن تحميل الأجهزة المستهدفة.

**المعالجة المقترحة:** قسّم الشاشات الكبيرة مثل الإدارة والخرائط إلى تحميل كسول، ثم قارن قياسات التحميل الفعلية قبل تعديل حد التحذير.

## ضوابط موجودة في الكود

- يفعّل المخطط الأساسي RLS على كل جداول `public` الموجودة عند تطبيقه، ويسحب صلاحيات SQL من `anon` و`authenticated` ويمنحها لخادم `service_role`. كما تسحب إعدادات الصلاحيات الافتراضية وصول العملاء إلى الجداول الجديدة. الجداول اللاحقة الحساسة تُفعّل RLS وتمنع الوصول المباشر صراحةً.
- تحقق Edge Function من جلسة معتمة عبر hash مخزن، ثم يرفض الجلسة المنتهية أو الملغاة، ويتحقق من الدور قبل المسارات المحمية.
- مستندات التحقق مخزنة بسياسات تمنع القراءة المباشرة من التخزين؛ عرضها يمر عبر مسارات التطبيق المحمية.
- لم يظهر في الفحص الساكن مسار عميل يكتب `admin` في التسجيل؛ التسجيل يقبل `rider` أو `captain` فقط. تبقى فجوة trigger المذكورة أعلاه دفاعًا إضافيًا مطلوبًا.

هذه مراجعة مصدرية فقط؛ لم تُختبر المنح والسياسات الفعلية على PostgreSQL في هذا التشغيل.
