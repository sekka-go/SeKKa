# seKKa — P0 Delivery Batch 01: Captain route safety
Date: 20 November 2026 · Branch: `feat/real-app-google-auth-foundation-20261115` · PR #185

## Scope and owner constraints
This batch **does not** approve or silently change the service-line/operational-trip architecture. It preserves the currently enforced one-published-or-paused-service-per-vehicle rule. It targets **Staging Supabase only** (`zgcvumykzivsvnlflbyp`), never Production. It does not change the approved seKKa typography, yellow/black branding, Google OAuth, deferred OTP/payments, or introduce a paid service.

## Grounded incident
The video showed `VEHICLE_HAS_ACTIVE_SERVICE` after finishing a draft. Read-only Staging inspection confirmed the existing `v31_guard_route_status` trigger rejects publication when another `published` or `paused` route uses that vehicle. At baseline at least one draft was in this situation. Previously the UI had no early warning and showed raw SQL errors.

## Implemented
1. `v31_create_geolocated_route_draft`: A **new**, restricted RPC wraps the existing approved-Captain draft-creation validation and previously audited stop-coordinate setter. It saves all coordinates within the same database transaction. If any stop write fails, the complete operation rolls back. The pre-existing RPC is retained to preserve other callers.
2. Captain draft UI sends stop coordinates through the new atomic RPC and removes client-side per-stop RPC writes. It still verifies saved route and coordinates by readback.
3. A vehicle-specific, Captain-scoped read-only preflight checks for currently published/paused routes as soon as an approved vehicle is selected. A conflict blocks progression to price; message offers navigation to My routes. The database trigger remains the ultimate authority.
4. A bilingual whitelist maps known SQL error codes to actionable messages. Unknown backend error details are no longer exposed to Captains. A failed publishing action no longer invites a meaningless retry-loop.
5. Captain search results now require matching **both** the selected service-area locality and the requested place name; a short whitelist of street aliases covers `شارع التسعين`/90th Street and `ميدان الحصري`/Al Hosary Square without fabricating coordinates.
6. Added unit and browser mocks for wrong landmarks, preflight conflict, and single-RPC coordinate persistence.

## Deferred deliberately (not approved automatically)
- **OD-01:** One `ServiceLine` vs dated `OperationalTrip` schema; vehicle use across non-overlapping schedules. The existing trigger is intentionally unchanged.
- **Pricing:** Do not silently create a new production price rule from approximate straight-line distance. The approved 7–12 EGP/km band, routing-distance sources, admin fallback and ownership of exceptions need a separate audited server-side implementation.
- **Place data:** Named landmarks and Photon locality do not create an authoritative polygon/POI catalog. An audited Cairo/Giza point catalog is a subsequent batch.
- **Existing draft duplicate retries:** This batch reduces partial saves; idempotency across repeated disconnected submits still needs a server-approved key/constraint.
- **Lifecycle:** Full -> Captain schedules departure -> cancellations return to search and invalidate the date; not simulated with UI-only placeholders.
- **Cancellation thresholds:** Owner approval required for PRIME and final category table; no automatic penalties implemented.
