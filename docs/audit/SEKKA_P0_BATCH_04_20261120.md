## Confirmed issue and remediation
- Before the fix the browser roles `anon` and `authenticated` had `TRUNCATE` on public tables including `v31_bookings` and `v31_routes`. Postgres RLS does NOT govern `TRUNCATE`. Migration `20261120204500` revoked `TRUNCATE` from both roles for every public table, including default privileges for future postgres-owned public tables.
- Staging privilege queries after the migration: 0 client-role `TRUNCATE` privileges across all current public tables; the booking RPC still executes; one original booking and two original routes were preserved.
- New migration `20261120210000` exposes `v31_rider_booking_fare_status(p_booking)`: amount + an explicit `is_exact` flag, scoped to the logged-in rider. New booking claims return the immutable saved seat fare, while legacy bookings still show only a clearly identified estimate. No historical booking price was rewritten. Removed direct anon/auth `INSERT`, `UPDATE`, `DELETE` grants on the bookings table; write operations stay in identity-checked RPCs.
- `BookingFlow.tsx` now distinguishes the **recorded** fare for new bookings from the **estimated** fare for legacy rows.
- Inspection of `v31_accept_trip_offer` showed it inserted a new booking without allocating its seat claim/price. Migration `20261120212000` inserts a call to `v31_allocate_booking_seat_prices(booking)` immediately after the new booking insert, atomically inside the pre-existing offer-acceptance RPC. The migration refuses to patch an unknown source version. All offer state checks, lock ordering, and transitions stay unchanged.

## Staging verification performed
- Read-only ACL checks confirmed that anon/auth can no longer `TRUNCATE`; public seat-price reads and authenticated booking RPC calls remain possible.
- Rollback-only last-seat test: first test rider reserved the only remaining seat, new fare matched the immutable booking snapshot, a second rider's reservation failed for insufficient capacity, cancellation did not reprice the first booking, and all test writes were rolled back. This was **sequential in a controlled transaction**, not a claim of parallel multi-connection stress testing.

- No production data, design tokens, OAuth, payments, recurring-line schema, or departure rules were changed.
