# SeKKa — تحليل الفجوات قبل التنفيذ

**نطاق المراجعة:** PRD سِكّة v1.0 بتاريخ 23 أكتوبر 2026، مستودع `sekka-go/SeKKa` محليًا، وتصدير Stitch المرفق. هذا فحص ساكن للمصدر والملفات فقط؛ لم تُنفذ تغييرات تطبيق أو قاعدة بيانات، ولم تُشغّل اختبارات أو نشرًا.

**طريقة القراءة:** الحالات هي `مطبق`، `جزئي`، `مفقود`، `متعارض`. وجود شاشة أو جدول لا يعني اكتمال قاعدة العمل أو أن النشر الحي مطابق. الأولوية للسلوك حسب PRD v1.0؛ تصميم Stitch يحدد المظهر فقط. عند تعارض التصميم مع قاعدة العمل، تُحفظ القاعدة ويُسجل قرار التصميم.

## 14. ملحق فحص الإنتاج وتحسين الرسائل — 23 أكتوبر 2026

- توضح README أن Express/SQLite هو نموذج التطوير المحلي القديم. واجهة الإنتاج تتصل افتراضيًا بـSupabase Edge؛ تم التحقق للقراءة فقط من مشروع Supabase `seKKa` في `eu-central-1` وحالته `ACTIVE_HEALTHY`، وقاعدة PostgreSQL 17. لم تُعرض بيانات شخصية ولم تنفذ أي كتابة أو migration.
- ظهرت 14 ملاحظة Security Advisor من نوع جداول RLS مفعلة بلا policy، لكن فحص الصلاحيات وجد عدم وجود منح `SELECT` لأدوار `anon` و`authenticated` على جداول `public` المفحوصة. هذا يتفق مع نمط منع الوصول المباشر واعتماد API الخدمة؛ لا تعتبر الملاحظات وحدها ثغرة مؤكدة، ولا ينبغي إضافة سياسات واسعة لإسكاتها.
- ظهرت 43 ملاحظة فهرس غير مستخدم. لم تُحذف فهارس؛ حجم البيانات/مدة الرصد لا يبرران الحذف الآن. سجلات المتاحة اقتصرت على PostgreSQL/PgBouncer، ولم تكن سجلات Edge Runtime متاحة.
- `MessagesWorkspace.tsx`: أُوقف polling عند إخفاء الصفحة، ومنع تداخله، وخُفّض تحديث المحادثات من كل 8 ثوانٍ إلى 20 ثانية (مع عدم إعادة تحميل جهات الاتصال دوريًا)، والرسائل المفتوحة من كل 3.5 ثوانٍ إلى 10 ثوانٍ. استدعاء تحديد الرسائل كمقروءة يحدث عند فتح المحادثة أو ظهور رسائل واردة غير مقروءة، بدل كل دورة polling.
- لم تُطبق تغييرات على Supabase/Cloudflare، ولم يحدث commit أو push أو نشر. سجل migrations البعيد اطلع عليه، لكن لم تتم مطابقة كاملة أو تحقق من النسخ الاحتياطية.
- لا تثبت هذه المراجعة قدرة 5,000 اتصال متزامن. لا يوجد اختبار حمل فعلي؛ أي استنتاج حول السعة يظل مشروطًا بخطة الاستضافة وحدود الموارد ومعدل الطلب.
- حدود Supabase المنشورة حاليًا للخطة المجانية تتضمن 500 ألف Edge Function invocation شهريًا، 500MB quota لحجم قاعدة البيانات، 5GB egress، 50 ألف MAU، 1GB storage و200 اتصال Realtime متزامن؛ مشاريع الخطة المجانية قد تتوقف بعد أسبوع خمول، ولا توفر نسخ قاعدة قابلة للتنزيل. الخطة الفعلية للمشروع وحدود استخدامها لم يمكن التحقق منها من صلاحية الأدوات المتاحة. [الخطط والفوترة](https://supabase.com/docs/guides/platform/billing-on-supabase)، [النسخ الاحتياطي](https://supabase.com/docs/guides/platform/backups)، [إيقاف المشاريع الخاملة](https://supabase.com/docs/guides/platform/free-project-pausing).
- نموذج حساسية توضيحي، وليس توقعًا للطلب الفعلي: 100 مستخدم يوميًا × 10 دقائق في مساحة الرسائل × 30 يومًا ينتج قرابة 270 ألف طلب polling شهريًا بعد التعديل (3 طلبات صندوق/دقيقة + 6 طلبات محادثة/دقيقة)، قبل سائر استخدام التطبيق. عند 500 مستخدم يوميًا يصبح نحو 1.35 مليون؛ يتجاوز حصة الدوال المجانية المنشورة. عند 5,000 جلسة متزامنة على الشاشة نفسها قد يصل الحمل إلى نحو 750 طلبًا/ثانية؛ لا يوجد دليل أن المشروع أو الخطة الحالية تتحمل ذلك.
- Cloudflare Pages Free ينشر بحد موثق 500 build شهريًا وبناء واحد متزامن؛ حدود البناء وحدها لا تحدد قابلية تحمل API أو قاعدة البيانات. [Cloudflare Pages limits](https://developers.cloudflare.com/pages/platform/limits/).
- لم يُجرَ اختبار حمل واقعي أو اختبار استرجاع نسخة احتياطية؛ لذا لا يمكن تأكيد شرط 5,000 MAU أو التزام «صفر تكلفة إضافية» دون إحصاءات استخدام وخطة مؤكدة ومراقبة حصص المشروع.
